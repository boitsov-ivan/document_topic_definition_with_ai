# ML System Design Doc - [RU]
## Дизайн ML системы - "Аналитик документов"

*Шаблон ML System Design Doc от телеграм-канала [Reliable ML](https://t.me/reliable_ml)*   
    
### 1. Цели и предпосылки
#### 1.1. Зачем идем в разработку продукта?  

- Бизнес-цель `Product Owner`
Создать сервис (Telegram-бота и веб-интерфейс), который автоматизирует первичный анализ документов любых тематик и поиск релевантных (похожих) документов. Сервис должен помочь пользователям быстро понять суть статьи (сниппет, саммари, список тем статьи) и найти наиболее релевантный контент в базе, экономя время на чтение и поиск.

- Почему станет лучше, чем сейчас, от использования ML `Product Owner` & `Data Scientist`  
Без ML мы не сможем автоматически выделить главную мысль из текста, классифицировать его по темам и найти похожие документы.
Клиентский путь без ML содержит много ручного труда:
1) прочитать документ, уяснить его смысл;
2) составить краткий пересказ документа, выделив его основные тезисы;
3) составить список тем документа и его ключевых слов;
4) провести поиск похожих документов, формируя запросы на основе краткого пересказа и списка тем документа.
С использованием ML исключается ручной труд, досточно направить в сервис документ и мгновенно получить результат.
ML позволит обрабатывать неограниченный поток статей автоматически и масштабировать сервис.

- Что будем считать успехом итерации с точки зрения бизнеса `Product Owner`  
Запущен работающий Telegram-бот и веб-сервис (стримлит), который для текста документа выдаёт осмысленный сниппет (краткий пересказ), список из 3-20 релевантных тем и 5-15 ссылок на похожие документы из нашей базы.
Качество ответов должно быть приемлемым для демонстрации потенциальным пользователям и сбора обратной связи.

#### 1.2. Бизнес-требования и ограничения  

- Бизнес-требования:
1) сервис должен принимать текст документа;
2) в ответ сервис выдаёт - краткий пересказ документа (10-30 предложений), список тем статьи (3-20), список похожих документов (заголовок и ссылка) из собственной базы сервиса (5-15 ссылок).
3) база данных сервиса наполняется статьями, собранными с Хабра.

- Бизнес-ограничения:
1) решение должно быть разработано в ограниченные сроки (MVP);
2) используются преимущественно open-source библиотеки и модели, чтобы минимизировать затраты;
3) точность на первых порах может быть не идеальной, но ответы должны быть адекватными.

- Что мы ожидаем от итерации:
Получить работающий прототип сервиса, который можно протестировать на фокус-группе.

- Бизнес-процесса пилота:
1) пользователь отправляет текст документа или текстовый файл в Telegram-бота или через форму сайта;
2) сервис получает сообщение, извлекает текст;
3) текст оправляется на внутренний API сервиса;
4) ML-модули сервиса обрабатывают текст - генерируют эмбеддинг, классифицируют темы, генерируют краткий пересказ;
5) модуль поиска ищет похожие документы по эмбеддингу, BM25, с реранжированием (пользователь сам изменяет настройки поиска);
6) сервис возвращает пользователю структурированный ответ.

- Критерии успешного пилота:
Сервис успешно обрабатывает тестовые запросы (ссылки, файлы) и выдаёт осмысленные ответы, которые оцениваются тестовой группой как "полезные" в 70% случаев. Отсутствие критических ошибок (падений сервиса).


#### 1.3. Что входит в скоуп проекта/итерации, что не входит   
Входит в скоуп:
1) сбор и парсинг данных с habr.com (заголовки, текст, тематики/хабы);
2) очистка и предобработка текстов;
3) обучение модели для получения эмбеддингов документов (BoW, TfIDF, ruBERT);
4) обучение модели для мультилейбл-классификации тематик;
5) обучение модели для генерации сниппетов;
6) разработка гибридного поиска похожих документов (эмбеддинги + BM25), поиска с реранжированием;
7) разработка Telegram-бота, стримлит сервиса и API-прослойки для взаимодействия;
8) написание кода, обеспечивающего воспроизводимость решения (Docker compose, requirements.txt);
9) высокая нагрузка и горизонтальное масштабирование (очереди RMQ и кубернетес).

Не входит в скоуп:
Поддержка других языков, кроме русского;

Результат с точки зрения качества кода:
1) код размещен в репозитории (github);
2) код содержит инструкцию по запуску (README.md), требования к окружению, Dockerfile для сборки образа.


#### 1.4. Предпосылки решения  

Данные собираются с Хабра.

Модели используются русскоязычные (семейство ruBERT, rut5) как наиболее релевантные для задачи.

Гранулярность модели: на уровне документа (статьи).

Горизонт прогноза: модели применяются к документу в момент запроса, переобучение планируется по мере накопления новых данных (раз в месяц).

Блоки данных: текст статьи (заголовок, тело).

Мета-информация: тематики (хабы, тэги), дата публикации, автор, ссылка.


### 2. Методология     

#### 2.1. Постановка задачи  

С технической точки зрения мы решаем комплекс задач:

1) feature engineering (получение векторных представлений (эмбеддингов) текстов);

2) мультилейбл-классификация (отнесение документа к одной или нескольким тематикам из заданного множества);

3) Seq2seq / Text Summarization (генерация краткого пересказа документа);

4) Information Retrieval (поиск наиболее похожих документов в коллекции).

#### 2.3. Этапы решения задачи
*Этап 1: Подготовка данных и EDA*
Цель: cобрать и подготовить датасет для обучения моделей.
Данные: парсинг сайтов habr.com, zakon.ru
Сущности документа: id, title, text, url, date, author, hub, tags, summary
Ресурсы: DS для написания парсера.
Качество данных: проверяется вручную на выборке из 100 статей (наличие полного текста, корректность тем).
Результат этапа: таблица documents с текстами и метаданными, проведён EDA (распределение длины текстов, распределение тем по частоте).

*Этап 2: Построение моделей*
Модель эмбеддингов
Цель: получить векторное представление документа для поиска похожих.
Формирование выборки: используются все тексты из базы.
Метрики качества: не оценивается напрямую, является частью пайплайна для поиска. Качество оценивается косвенно через релевантность поиска (NDCG@k, Recall@k).
Алгоритм решения: используем предобученную SOTA модель для русского языка intfloat/multilingual-e5-large, cointegrated/rubert-tiny2, sergeyzh/rubert-tiny-turbo. Эмбеддинг получаем усреднением токенов последнего скрытого слоя (mean pooling). Модели не дообучается на этапе MVP (используются как Feature Extractor).
Риски: модель может плохо понимать специфику IT-контента.
Результат этапа: Ффнкция для преобразования текста в эмбеддинг размерности, например, 768 или 384.


Модель классификации тематик
Цель: определить темы документы (мультилейбл-классификация).
Формирование выборки: текск статьи.
Целевая переменная (y): бинарный вектор, где каждая позиция соответствует одной теме.
Обработка: убираем темы, которые встречаются слишком редко (например, менее чем в 50 документах).
Гранулярность: На уровне документа.
Метрики качества: Точность (Precision), полнота (Recall), F1-мера (micro/macro) на валидационной выборке.
Алгоритм решения: берём предобученную модель DeepPavlov/rubert-base-cased, добавляем на выход слой классификации с sigmoid активацией. Дообучаем (fine-tune) всю модель целиком.
Кросс-валидация: разбиение данных по времени (train на старых статьях, validation на новых), чтобы избежать "data leakage".
Риски: дисбаланс классов (некоторые хабы очень редкие). Решение — использование взвешенной функции потерь (BCEWithLogitsLoss с весами, обратными частоте классов).
Результат этапа: обученная модель, которая для текста возвращает вероятность принадлежности к каждой теме.

Модель генерации сниппетов (Summarization)
Цель: генерация краткого пересказа (10-30 преддложений).
Формирование выборки: X - текст статьи, y - саммари.
Проблема: у нас нет готовых саммари для статей.
Решение для MVP: получаем саммари с помощью АПИ больших языковых моделей
Метрики качества: ROUGE-1, ROUGE-2, ROUGE-L. Для MVP — экспертная оценка адекватности. Обучаем модель на основе полученной выборки, проводим дистилляцию большой модели.
Результат: функция, которая на вход принимает текст, а на выходе отдает 10-30 предложений в качестве сниппета.


Поиск похожих документов
Цель: по эмбеддингу документа найти 5-15 самых близких в базе.
Метрики качества: оцениваем релевантность найденных документов вручную или через NDCG@k (после разметки похожих).
Алгоритм решения:
- семантический поиск (индексируем все эмбеддинги документов из базы с помощью библиотеки FAISS, поиск по косинусной близости);
- лексический поиск (строим BM25 индекс по текстам документов).
- получаем топ-N кандидатов от FAISS и топ-M от BM25,  объединяем списки, удаляем дубликаты и ранжируем финальный список с помощью ранговой суммы (RRF).
Риски: поиск по всей базе может быть медленным.
Решение: кэширование частых запросов.
Результат этапа: сервис, который по тексту документа возвращает список ID похожих документов.

  
### 3. Подготовка пилота  
  
#### 3.1. Способ оценки пилота  
Пилот запускается в закрытом режиме для группы из 10-15 добровольцев. Им выдается ссылка на бота и инструкция.
Количественная оценка: сбор логов работы сервиса (количество запросов, типы ошибок, время ответа).
Качественная оценка: опрос пользователей после использования. Им предлагается оценить по 5-балльной шкале: полезность сниппета, точность определения тематик, релевантность похожих статей.
Ручная валидация: DS вручную просматривает 500 ответов бота на разные запросы, оценивая их адекватность.

#### 3.2. Что считаем успешным пилотом  
Бот отработал без падений (uptime > 95%).
Средняя оценка пользователей по каждому из трех параметров (сниппет, тематики, похожие) >= 4.0.
Мы собрали не менее 500 оценок от пользователей.
Выявлены и зафиксированы основные проблемы для следующей итерации.
  
#### 3.3. Подготовка пилота  
Вычислительные ресурсы: для пилота достаточно одной GPU. Основные затраты — память для хранения индекса FAISS (индекс может занимать несколько гигабайт).
Ограничения: время ответа тяжелой модели для эмбеддингов (E5) может быть большим. Придется оптимизировать (батчинг, использование GPU).
Поиск по FAISS может потребовать много RAM.
Планируем замерить время инференса каждой модели и поиска на тестовой нагрузке (1 RPS) в процессе разработки, чтобы принять решение об оптимизации.

### 4. Внедрение
#### 4.1. Архитектура решения   
Система состоит из трёх основных микросервисов:
1) Telegram Bot и веб-сервис на джанго - отвечает за взаимодействие с пользователем, принимает сообщения, отправляет ответы.
2) API Server - центральное звено. Получает текст, вызывает по очереди ML-сервисы, агрегирует результат и возвращает.
3) ML Services - Embedder (FAISS index в памяти), Classifier, Summarizer;
4) база данных (PostgreSQL) - хранит тексты статей и метаданные.

Схема взаимодействия:
Telegram Bot (веб-сервис на джанго) <-> API Server <-> ML Service(s) & PostgreSQL (через API Server)
  
#### 4.2. Описание инфраструктуры и масштабируемости
  
Инфраструктура: Docker-контейнеры, оркестрируемые через кубернетес.

Почему такой выбор: возможности масштабирования по нагрузке.

Масштабирование: при росте нагрузки самое узкое место — ML-сервисы (требуют CPU/GPU). Их можно будет вынести на отдельные машины и горизонтально масштабировать за балансировщиком. FAISS индекс можно хранить в памяти каждого экземпляра ML-сервиса (репликация).
  
#### 4.3. Требования к работе системы  
SLA: 95%.
Задержка (Latency): общее время ответа бота не должно превышать 5-7 секунд для 90% запросов (с учетом генерации эмбеддинга и поиска). Это жесткое требование UX.
  
#### 4.4. Безопасность системы  
Потенциальная уязвимость: API сервиса может быть доступен извне. Необходимо настроить аутентификацию запросов от бота (например, по API-ключу). Telegram бот защищен токеном.
DOS-атаки: парсинг ссылок от пользователей — потенциальный риск, если пользователь отправит ссылку на вредоносный ресурс. Нужно использовать безопасные библиотеки для запросов и парсинга.
  
#### 4.5. Безопасность данных   
  
Нарушений GDPR и иных законов нет.
  
#### 4.6. Издержки  
Расчётные издержки (облачный сервер, ед. измерения — ₽/мес):
Сервер (4 vCPU, 16 GB RAM, 100 GB SSD): ~5000-7000₽.
GPU (если потребуется для скорости инференса, например, Tesla T4): ~10 000-15 000₽.
Итого: 5000 - 22 000₽ в месяц в зависимости от потребности в GPU.

#### 4.7. Integration points  
  
Telegram Bot -> API Server: HTTP POST-запросы с текстом документа.

API Server -> ML Service(s): синхронные gRPC или HTTP вызовы. Самый простой вариант — HTTP (FastAPI внутри ML-сервисов).

API Server -> PostgreSQL: SQL-запросы для получения метаданных по ID найденных документов.
  
#### 4.6. Риски  
  
Медленные модели: самая большая модель (суммаризации/эмбеддингов) может не укладываться в требования по задержке.
Митигация: использовать более легкие модели (rubert-tiny, обучим свою малую модель с помощи дистилляции болшой языковой модели), кэшировать результаты для частых запросов, использовать GPU.
"Холодный старт" для новых тем: если появится документ по совершенно новой теме, которой нет в базе, поиск похожих может быть плохим.
Митигация: регулярное (раз в неделю) дообучение модели эмбеддингов и переиндексация базы.
